Components in SMMUv3 interface:
	TCU: Translation Control Unit
	TBU: Translation Buffer Unit
	PCIe Root Port with Address Translatio Service support
	DTI Interconnect

DTI protocol is of two types: 
	Between TBU and TCU
	Between PCIe Root Port with TCU

Where DTI interconnect comes-> between TBU and TCU, or a PCIE root which would communicate to TCU

There are two main parts: DTI Masters or TBU, DTI slaves or TCU
From Master to TCU it is downstream, from TCU to master is is Upstream

Each transfer can be divided into message type and payload, with fixed defined widths

Messages can be of multiple types
	Connect/Disconnect : Power Domain and credit bargain mechanism
	Translation Request
	Invalidation and Synchronisation
	Register Access
	Page Request

Flow Control
	Tokens: How many outstanding messages of a group are allowed
	Request consumes tokens and response return them
	Ids are used to track outstanding transactions, unique per transaction
	
DTI Connections:
	Channel states: Disconn, connec, req_connect, req_disconnect, requests are send by _M
	DTI channels are point to point, if there are multiple TBU, each TBU TCU connection would have separate channel

DTI interconnect:
	The protocol level things of extracting fields from message is work of endpoints, not interconnect
	Major work of it would be arbiteration of requests from multiple masters and demux the responses
	it needs to ensure all beats of transaction are transported before next TBUs message can start, maybe bring ready low for other TBUs
	But this does not mean that only one channel tell tokens get over
	Token and states are responsibility of the endpoints
	Interconnect must mantain ordering, atleast for a transactions, and for transactions in same channel, but not sure among different channels
	
DTI Channel Lifecycle:

	Master sends the REQ and TCU send the ACK

  └──────────────┘                          └─────────────┘
          ▲                                        │
          │ CONDIS_ACK (STATE=0)                   │ CONDIS_ACK (STATE=1) (State can be 0 meaning reject the request)

	This sequence is performed for enablling a channel, when TBU swithces from power down state or goes to it, this connection is required
	The request contains other parameters like the TBU version, credit bargains, power domains, stages etc
	Both agree for common parameters supported by both or the TCU declines the channel connection request

Translation Request:
	When the translation is not present in the cache of TBU, it sends a transaltion request to TCU
	The request mentions the address which needs to be transalted, this request uses one credit if the tbu
	The request contains other parameters like translation ID, security attributes, stream and substream id
	when the tcu responds to this address, it tells the translated address and for what adddress range this translation is valid using Trans Range
	This trans range is the space which has all those stream/subtream/security features same

Stream ID/Substream Id:
	Identifies the stream and substream of which the transaction is part of, ie tell that it comes from GPU(SID) and then which GPU core(SSID)
	That particular page table would be used then
	But then for axi transaction this information also needs to be communicated
	Done using Untranslated Transaction signalling, present in AXI interface if Untranslated Transaction is v2

MMU signals in AXI and corresponding in DTI
	AxMMUSID: Stream Identifier or SID in DTI
	AxMMUSSIDV: SSIDV-> Substream is valid for this transaction
	AxMMUSSID: SSID Substream Id
	AxMMUFLOW: 2 bits signal to tell how should faults be handled
	RESP:  BRESP and RRESP contain rsp opcode for Translation fault as well
        MMUV signal in DTI:  There is no corresponding in AXI, this tells if translation should be performed or only GPC check need to be performed	

FLOW:
	This tells how are faults handled:
		STALL: the device tells that stall are accepted, so if TCU does not find the address, it does it routine to bring it from DDR and translation is stalled till then
		NO STALL: Stall cannot be tolerated, fault is given
		PRI: PCIE related, PCIE endpoint asks OS to fill the RAM with translated address, TCU returs fault from its end
		ATST:  Address was already translated, not the normal translation fault, translation alrady occured

MMUV:	
	Tells whether translations need to be performed or only granule protection checks need to be performed
	During channel sonncetion itself there is a STAGES filed which tells what all values of MMUV are permitted
		STAGES=M  MMUV should be 1 only
		STAGES=G  Only GPC, MMUV=0
		STAGES=GM  Both are allowed	
	
GPC:
	Granule Protection Checks
	Memory is divided into granules and GP Tables tell which part is in which security domain
	GP fault is raised if a device with one acces tries to acces that of higher access
	There are other persmissions like read write permissions etc, they dont come under gpc, they come from PERM
